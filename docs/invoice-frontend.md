# فاکتور بعد از تسویه — راهنمای فرانت

فاکتور را فرانت نمی‌سازد. بعد از تسویهٔ موفق زرین‌پال، بک‌اند برای همان سفارش یک سند فریزشده می‌سازد. دکتر مالک و ادمین آن را می‌خوانند یا PDF می‌گیرند. ادمین یک پروفایل فروشندهٔ سراسری دارد که فقط روی فاکتورهای بعدی کپی می‌شود.

همهٔ مسیرها زیر `/api` هستند. احراز هویت با هدر `Authorization: Bearer <token>` است.

شکل پاسخ JSON موفق:

```json
{
  "status": 200,
  "success": true,
  "data": {},
  "resultMessage": "..."
}
```

شکل پاسخ خطا:

```json
{
  "status": 400,
  "success": false,
  "error": "...",
  "data": null
}
```

زبان `error` و `resultMessage` فارسی است. دانلود PDF این پوشش JSON را ندارد.

## چه وقت فاکتور وجود دارد

دکمهٔ فاکتور فقط وقتی پرداخت واقعاً تسویه شده نشان داده شود:

- `orders.paymentstatus === true`
- `payment.status === "paid"`

قبل از تسویه، و بعد از پرداخت ناموفق، فاکتور نیست. `GET` فاکتور در این حالت `404` با پیام `فاکتور یافت نشد` برمی‌گرداند. این `404` را خطای برنامه حساب نکنید؛ یعنی هنوز سندی ساخته نشده.

هر سفارش حداکثر یک فاکتور دارد. بازگشت تکراری درگاه سند دوم نمی‌سازد. فرانت callback زرین‌پال را صدا نمی‌زند.

تغییر بعدی قیمت دسته، متریال، درصد مالیات، یا پروفایل فروشنده، فاکتورِ صادرشده را عوض نمی‌کند. برای دیدن مقادیر تازه، سفارش جدیدی باید بعد از آن تغییر تسویه شود.

## خواندن فاکتور

`GET /api/order/order/:id/invoice`

دکتر فقط سفارش خودش را می‌بیند. ادمین هر سفارشی را می‌بیند.

| وضعیت | پیام |
| --- | --- |
| 200 | `فاکتور با موفقیت دریافت شد` |
| 403 | `شما مجاز به دسترسی به این سفارش نیستید` |
| 404 | `سفارش یافت نشد` یا `فاکتور یافت نشد` |

`data` سند فاکتور است. مبلغ‌های `*Rial` عدد صحیح ریال‌اند. `paidToman` مبلغ تومانِ تسویه‌شده است و `totalRial` دقیقاً ده برابر آن است. ستون تخفیف و عوارض صفرند. فروش نقدی است: `cashRial` برابر `totalRial` و `nonCashRial` برابر `null`.

خانه‌های `null` را خالی نشان دهید و با عدد یا متن جایگزین پر نکنید.

خریدار:

- `name` نام لابراتوار است اگر در پروفایل کاربر پر باشد؛ وگرنه نام و نام خانوادگی.
- `phone`، `address` و `postalCode` از پروفایل کاربر در لحظهٔ تسویه می‌آیند. خالی بودن آن‌ها صدور را متوقف نمی‌کند.
- `economicNumber`، `nationalId` و `city` همیشه `null` هستند. برای خریدار این سه ورودی را نسازید.

فروشنده همان مقادیر پروفایل فروشنده در لحظهٔ تسویه است. اگر آن موقع پروفایل خالی بوده، هر هشت خانه `null` می‌ماند.

سطرها:

- هر دندان یک سطر با `quantity` برابر `1` است. شرح شامل عنوان دسته، شماره دندان و نام بیمار است.
- اگر سفارش VIP باشد یک سطر با شرح `خدمات ویژه` دارد.
- اگر جمع سطرها با مبلغ پرداخت نخواند، فقط یک سطر با شرح `خدمات لابراتوار` و همان جمع پرداخت‌شده می‌آید.
- `productCode` همیشه `null` است.
- `taxNumber` همیشه `null` است. این شمارهٔ سامانه مودیان نیست.
- `copies` سه برچسب نسخه است، نه سه فاکتور.
- `stamp` و `signature` همیشه `null` هستند. جای مهر و امضا را خالی بگذارید.

`issuedAt` زمان UTC است. اگر خودتان تاریخ را نشان می‌دهید، با منطقهٔ `Asia/Tehran` قالب‌بندی کنید. PDF بک‌اند همین کار را می‌کند.

`notes` توضیح سفارش و در صورت وجود، خط `کد پیگیری: ...` است.

## دانلود PDF

`GET /api/order/order/:id/invoice/download`

همان قاعدهٔ دسترسی و همان `403` / `404` خواندن فاکتور. در موفقیت بدنه فایل PDF است، نه JSON.

- `Content-Type: application/pdf`
- `Content-Disposition: attachment; filename="invoice-{orderId}.pdf"`

درخواست را با توکن بزنید و پاسخ را به‌صورت blob ذخیره کنید. اگر `status` خطاست، بدنه JSON خطا است.

چیدمان PDF جدول خط‌کشی‌شده است: مشخصات فروشنده، مشخصات خریدار، جدول کالا، نقدی و غیرنقدی، توضیحات، جای مهر و امضا، و چهار خانهٔ نسخه (فروشنده، خریدار، حسابداری، انبارداری). فرانت لازم نیست PDF را دوباره بسازد.

## پروفایل فروشنده

این فرم فقط برای ادمین است. دکتر پروفایل را نمی‌خواند و نمی‌نویسد؛ بلوک فروشنده را فقط داخل فاکتور سفارش می‌بیند.

`GET /api/invoice/seller-profile`  
`PUT /api/invoice/seller-profile`

اگر هنوز ذخیره نشده باشد، `GET` باز هم `200` است و هر هشت خانه `null` است. `404` به معنی پروفایل خالی نیست.

| وضعیت | پیام |
| --- | --- |
| 200 خواندن | `پروفایل فروشنده با موفقیت دریافت شد` |
| 200 ذخیره | `پروفایل فروشنده با موفقیت ذخیره شد` |
| 400 | `خطای اعتبارسنجی` |
| 403 | `شما مجوز انجام این عملیات را ندارید` |

`data` بعد از خواندن و بعد از ذخیره:

```json
{
  "name": null,
  "phone": null,
  "address": null,
  "postalCode": null,
  "economicNumber": null,
  "nationalId": null,
  "registrationNumber": null,
  "city": null
}
```

هیچ خانه‌ای الزامی نیست. رشتهٔ خالی یا حذف‌شده `null` ذخیره می‌شود. `PUT` کل پروفایل را جایگزین می‌کند؛ فرم باید هر هشت خانه را بفرستد، حتی آن‌هایی که خالی می‌مانند. فرستادن فقط خانه‌های تغییرکرده، بقیه را پاک می‌کند.

سقف طول:

| خانه | حداکثر |
| --- | --- |
| `name` | ۲۵۵ |
| `economicNumber` | ۶۴ |
| `nationalId` | ۶۴ |
| `registrationNumber` | ۶۴ |
| `postalCode` | ۲۰ |
| `city` | ۱۰۰ |
| `address` | ۲۰۰۰ |
| `phone` | ۳۰ |

ذخیرهٔ این فرم فاکتورهای قبلی را عوض نمی‌کند. متن فرم باید بگوید مقادیر از تسویهٔ بعدی روی فاکتور جدید می‌آیند.

پروفایل خالی یا ناتمام جلوی پرداخت و صدور فاکتور را نمی‌گیرد. دکمهٔ پرداخت را به پر بودن این فرم وابسته نکنید.

## کارهایی که فرانت نباید بکند

- ساختن فاکتور قبل از `payment.status === "paid"`
- صدا زدن callback زرین‌پال
- پر کردن شماره اقتصادی، شناسه ملی یا شهر خریدار
- ساختن کد کالا، شماره مالیاتی، مهر یا امضا
- فرض کردن اینکه ویرایش پروفایل فروشنده فاکتورهای قبلی را به‌روز می‌کند
- نشان دادن دو فاکتور برای یک سفارش
